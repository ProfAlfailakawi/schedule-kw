# دليل كتابة وحدات وثيقة المتطلبات

هذا الدليل لمن يكتب أو يحدّث ملفاً في `docs/srs/modules/`. كل وحدة ملف JSON واحد، وكل نص فيه **ثنائي اللغة** `{ "ar": "...", "en": "..." }`.
تُولَّد منها الصفحة التفاعلية وملفّا PDF (العربي والإنجليزي)، فلا يُكتب شيء في مكانين.

```
node scripts/srs/validate.mjs docs/srs/modules/<ملفك>.json   # يجب أن ينتهي بلا أخطاء
```

## 1. المبدأ

الوثيقة تصف **النظام كما هو في الكود**، لا كما تقول الوثائق وحدها. المصادر بترتيب الثقة:
الاختبارات (`tests/`) ← الكود (`src/server`, `src/components`, `src/utils`) ← الوثائق (`docs/*.md`, `README.md`) ← الاستنتاج.
- كل ما يثبته كود أو اختبار يُكتب بحالة `implemented` مع مرجعه.
- ما تذكره وثيقة ولا تجده في الكود يُكتب `planned` أو `in-progress` بحسب ما تجده.
- ما استنتجته ولم تجد له اختباراً: `"inferred": true` (يظهر في الوثيقة بوسم «مستنتج»).
- **لا تخترع ميزة.** إن لم تتأكد، افتح الملف وتحقق. الأرقام (حدود، مهل، أطوال، عدد المحاولات) تُنقل من الكود حرفياً.

## 2. شكل الملف

```jsonc
{
  "id": "SCH",                    // ثلاثة أحرف كبيرة، فريد
  "order": 4,                     // ترتيب الفصل
  "icon": "calendar-range",       // اسم أيقونة lucide (kebab-case) موجودة فعلاً في lucide-react
  "title":   { "ar": "...", "en": "..." },
  "tagline": { "ar": "...", "en": "..." },      // سطر واحد
  "summary": { "ar": "...", "en": "..." },      // 3–5 جمل: ماذا تفعل الوحدة ولمن ولماذا
  "actors": ["departmentHead", "committeeChair"],   // من docs/srs/actors.json فقط
  "sources": ["src/server/routes/schedulesRoutes.ts", "src/utils/schedule*.ts"],  // كل ملف تغطيه الوحدة (globs)
  "screens":   [ { "name": {..}, "file": "src/components/X.tsx", "note": {..} } ],
  "journeys":  [ { "actor": "departmentHead", "title": {..}, "steps": [ {..}, {..}, {..} ] } ],   // 3–9 خطوات قصيرة
  "diagrams":  [ { "id": "sch-flow", "type": "flow", "layout": "lr", "title": {..}, "caption": {..},
                   "nodes": [ { "id": "a", "label": {..}, "icon": "file-plus", "kind": "start" } ],
                   "edges": [ { "from": "a", "to": "b", "label": {..} } ] } ],
  "matrix":    { "title": {..}, "cols": [ {..} ], "rows": [ { "actor": "dean", "cells": [2,1,0] } ] },   // اختياري: 0 لا، 1 قراءة، 2 كتابة
  "requirements": [ /* انظر 3 */ ],
  "edgeCases": [ { "title": {..}, "scenario": {..}, "behavior": {..}, "evidence": ["tests/x.ts"] } ],
  "terms":     [ { "ar": "شعبة", "en": "Class section", "def": {..} } ],
  "ownerRules":[ {..} ]           // قرارات المالك الثابتة المتعلقة بالوحدة (README.md «Standing Rules»)
}
```

`kind` للعقدة: `start` `state` `decision` `end` `system`. العقد 3–14، والعنوان قصير (≤ 4 كلمات). المخطط يجب أن يُظهر **آلية حقيقية** (حالات، قرارات، تدفق)، لا قائمة.

## 3. المتطلب

```jsonc
{
  "id": "FR-SCH-012",            // FR وظيفي · NFR غير وظيفي · DR بيانات · IR واجهة  +  رمز الوحدة  +  ثلاثة أرقام
  "kind": "functional",          // functional | nonfunctional | data | interface  (يطابق البادئة)
  "title": { "ar": "كشف تعارض القاعة", "en": "Room conflict detection" },
  "text":  { "ar": "يجب على النظام ...", "en": "The system shall ..." },
  "rationale": { "ar": "...", "en": "..." },       // اختياري: لماذا
  "priority": "must",            // must | should | could
  "status": "implemented",       // implemented | in-progress | planned
  "actors": ["committeeChair"],
  "acceptance": [ { "ar": "...", "en": "..." } ],  // معايير قبول قابلة للقياس (واحد على الأقل)
  "evidence": { "code": ["src/server/core/scheduleConflicts.ts"], "tests": ["tests/schedule-conflicts-audit.ts"] },
  "inferred": false
}
```

- **متطلب واحد = قدرة واحدة قابلة للاختبار.** صيغة «يجب على النظام …» / «The system shall …».
- معيار القبول يصف ما يُلاحَظ (مدخل ← نتيجة) بأرقام الكود الفعلية.
- أرقام المتطلبات تتسلسل من 001 بلا فجوات متعمدة، ولا تُعاد استعمالها بعد حذف (يُحوَّل المتطلب إلى `planned` أو يُنقل).
- مراجع `evidence` تُفحص آلياً: يجب أن يكون المسار موجوداً. يجوز `#رمز` بعد المسار.
- الحجم المطلوب لكل وحدة: **14–30 متطلباً** (أكثر للوحدات الكبيرة)، 3–6 حالات حدية، رحلتان على الأقل، مخطط واحد على الأقل. لا حشو؛ كل متطلب يحمل معلومة محددة.

## 4. الأسلوب (ملزم)

**اللغة الإنجليزية** هندسية دقيقة (shall/must)، **والعربية** فصحى هندسية طبيعية قريبة من مصطلحات الشاشات نفسها (انظر نصوص الواجهة). لا حشو ولا مبالغة ولا عبارات قوالب.

عبارات **ممنوعة** في كل نص مقروء (يفحصها المدقق ويفشل بها): `ذكاء اصطناعي`، `الذكاء`، `ذكي/ذكية`، `AI`، `artificial intelligence`، `machine learning`، `LLM`، `GPT`، `chatbot`، `language model`، `smart`، `intelligent/intelligence`، `نموذج لغوي`، `تعلم الآلة`، وكل ما يوحي بطريقة إعداد الوثيقة أو أدواتها.
- شاشة «مركز الذكاء» تُسمّى في الوثيقة **«مركز التحليلات / Analytics Center»**، و«الاستيراد الذكي» تُسمّى **«الاستيراد المساعَد / Assisted import»**، و«المرشد» يبقى «المرشد / Guide». لا تصف أي ميزة بأنها «ذكية».
- **Gemini** يُذكر باسمه **فقط** في وحدات `IMP` و`INT` و`EXT` و`NFR`، بصياغة محايدة: «خدمة Gemini تقرأ النص وتقترح؛ والتنفيذ دائماً عبر المدققات الحتمية وبتأكيد صريح من المستخدم».
- لا أسماء أدوات تطوير ولا إشارة لكيفية كتابة الكود أو الوثيقة.
- لا أسماء أشخاص حقيقيين (أساتذة، طلاب، موظفين) ولا معرّفات مشاريع سحابية ولا أسرار ولا قيم مفاتيح؛ استعمل الأدوار.
- **رقم المقرر سبع خانات دائماً** في أي مثال (كلية 2 + قسم 2 + مقرر 3، مثل `0109105`). لا تعرض `CourseCode` ثلاثي الخانات ولا `AdCourseId`.
- التقارير المطبوعة تحافظ على تصميمها (قرار المالك): اذكر ذلك حين يخصّ الوحدة.
- **المصطلحات:** استعمل نفس الكلمة العربية ومقابلها الإنجليزي في كل الوحدات. «القسم» = Department (في الكود `sectionId`)، و«الشعبة» = Class section / Offering، «الفصل» = Term، «المقرر» = Course، «الكلية» = College، «القاعة» = Hall / Room، «المبنى» = Building، «الصحيفة» = Plan sheet، «الجدول» = Schedule، «المسودة» = Draft، «الاعتماد» = Approval. قبل أن تبتكر مقابلاً افتح `docs/srs/modules/*.json` الموجودة وكرّر ما استُعمل.

## 5. التغطية والتتبّع

- `sources` تعدّد **كل** ملف تُحكم الوحدة سلوكه: ملفات المسارات، المنطق في `src/server/core` و`src/utils`، الشاشات في `src/components`. يتحقق CI من أن كل ملف في المجلدات المراقبة تدّعيه وحدةٌ ما.
- كل مسار خادم جديد (`app.get/post/...`) يُحسب تلقائياً على الوحدة التي تدّعي ملفه؛ ولقطته في `docs/srs/endpoints.snapshot.json` (`npm run srs:sync`). إضافة مسار بلا تحديث اللقطة تُفشل CI.
- عند إضافة ميزة: أضف متطلبها في وحدتها بحالة `implemented` مع الكود والاختبار، في **التغيير نفسه**. وعند إزالة ميزة: حوّل متطلبها إلى `planned` أو احذفه مع ذكر ذلك في `docs/srs/revisions.json`.
- تُولَّد الوثيقة بـ`npm run srs:build`، وملفا PDF بـ`npm run srs:pdf`.
