# آلة الزمن ومحاكي الشعب (L1 · L2)

مذكرة معمارية قصيرة: ماذا أُعيد استعماله، وما الفجوات الحقيقية التي سُدّت، وكيف يعمل.

## الفكرة
السيناريو **طبقة تغييرات (Overlay)** فوق الجدول الحيّ، كفرع في git: قائمة مرتبة من
`move | assign | remove | add`. تُطبَّق على نسخة، وتُقاس النسختان بالمقاييس نفسها، ولا يُكتب
شيء في الجدول قبل «اعتمد الكل».

## ما أُعيد استعماله (بلا نسخ منطق)
| السؤال | المحرّك القائم |
|---|---|
| التعارض المادي (مانع الاعتماد) | `findConflicts` + `isBlockingConflict` (scheduleIntelligence) |
| فجوات الأساتذة | `instructorGapStats` |
| النصاب | `weeklyLoadOf` (instructorRequestVerdict) + `teachingLoadLimits` / `AdInstructorLoad` |
| اللائحة 1912/1913 | `reviewSchedule` (scheduleRegulations) |
| سلسلة الدومينو | `planDisruption` / `findRepairChain` (repairChain) |
| تقليل الفجوات | `autoScheduleProposal` |
| ملاءمة القاعة | `roomSuitability`، والقاعات المسموحة `eligibleHallsForSection` |
| رقم الشعبة الجديدة | `nextCourseSectionCode` |
| «هيئة تدريسية» | `placeholderInstructorIds` (مرونة: لا تُحجز مرتين) |
| قراءة الجملة | `parseNaturalQuery` (اليوم) + مطابقة حتمية لأسماء القاعات/الأساتذة/المقررات الحقيقية |
| الطلبة | رادار التسجيل `RegistrationRun.courses` (جالسون/طلب/شعب) — لا تخمين؛ بلا رادار يظهر «—» |
| أثر مساري | `evaluateScheduleChange` + `loadSimulationInput` (simulationData) |
| الحفظ المركزي | `createScheduleHandler` / `updateScheduleHandler` في وضع `dryRun` على `hypotheticalWeek` |
| القفل | `acquireScheduleApplyLease("term-<id>")` نفسه الذي يقف عليه تثبيت رغبات الأساتذة |
| النسخ والاعتماد الرسمي | `captureScopeVersion` / `recordVersionAfter` / `noteScheduleMutation` (يعيد الجدول إلى دورة الاعتماد كأي تعديل؛ التوقيع في مساره) |
| النشر | روابط «بطاقات الأساتذة» الشخصية `/api/share/:id/personal` + `reachAboutCard` (واتساب يضغطه المنسّق) |

## الفجوات الحقيقية التي سُدّت
1. **لا سيناريو محفوظ** يجمع تغييرات متعددة بأنواعها → `TmScenarioRecord` في مجموعة `timeMachineScenarios` (اسم، وضع، تغييرات، إصدارات الأساس، مشاركة للعرض، سجل، نقطة استعادة).
2. **لا اعتماد ذري متعدد الأنواع** (نقل + إسناد + حذف + إضافة) خارج طلبات الأساتذة → `Repository.commitTimeMachinePlan`: معاملة Firestore واحدة (أو قفل تسلسلي في الديمو) تعيد قراءة الفصل، وتفحص إصدار كل صف، وحجوز الطلبات، ونوافذ الاستعارة، والتعارض على الأسبوع النهائي، ثم تكتب الصفوف ووثيقة السيناريو معاً — أو لا شيء.
3. **لا استعادة بنقرة** → نقطة استعادة (صور الصفوف قبل، والمنشأ، وإصدارات ما بعد) تُكتب في المعاملة نفسها؛ الاستعادة تُرفض إن عدّل أحدٌ الصفوف بعد الاعتماد.
4. **لا تنبيه انحراف** → `driftOf(live, base)`: صفٌّ يمسّه السيناريو حُذف أو تغيّر إصداره.
5. **لا مقارنة حلول بفلسفات مختلفة** → `solveProblem` (أقل تغيير، الطلبة أولاً، راحة الأساتذة، قاعات أقل، مرونة «هيئة تدريسية»)، ولا يُعرض حلٌّ يزيد موانع الاعتماد.

- `src/db/repository.ts` — CRUD السيناريو و`commitTimeMachinePlan`.
- `src/components/TimeMachine.tsx` (⏳ شاشة في القائمة)، `SectionSimulator.tsx` (🧩 تبويب بجانب «تخطيط الشعب»)، `ScenarioWorkbench.tsx`، `timeMachineShared.tsx`، `src/styles/33-time-machine.css`.
- `tests/time-machine-audit.ts` (`npm run test:time-machine`).

## الصلاحيات
- **القراءة والمحاكاة**: من يقرأ الجدول (`7,8,9,10,14,16,17`) بحدود نطاقه؛ العميد يقرأ النسخة المقبولة.
- **الحفظ/المشاركة/الاعتماد/الاستعادة**: إذن 7 وصفة غير قارئة فقط — في الخادم. غير الكاتب يرى ما شورك معه للعرض.
- بقية الفصل تصل **مقنّعة** (وقت وقاعة بلا اسم مقرر أو قسم؛ الأستاذ يبقى فقط إن كان من أساتذة النطاق) — تكفي لفحص الحجز المزدوج ولا تكشف بيانات قسم آخر.

## الحدود الحالية (صادقة)
- «د. X معتذر الخميس» يُعامل كعدم إتاحة للفصل (تغيير دائم). الغياب ليومٍ واحد مكانه «بديل اليوم» القائم.
- عدد طلبة الشعبة تقدير: جالسو المقرر في الرادار ÷ شعبه وقت القياس.
- تقسيم الشعبة يضيف شعبة أخت؛ توزيع الطلبة الفعلي يتم في التسجيل.
- الاستعادة إلى موضعٍ كان فيه تعارض قديم تُرفض من مسار الحفظ المركزي (لا يُعاد إنشاء حجز مزدوج).
- النشر يجهّز رسالة واتساب برابط البطاقة الشخصية؛ الإرسال يضغطه المنسّق (لا إرسال آلي). اشتراك التقويم (`/api/public/ics/:token`) يُبنى من رابط النشر عند كل مزامنة، فلا رابط جديد يلزم.
