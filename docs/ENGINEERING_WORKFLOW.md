# سير العمل الهندسي وسياسة النظافة

## الدورة اليومية

1. فرع ميزة أو إصلاح من `main`: `feature/<وصف>` أو `fix/<وصف>` أو `maintenance/<وصف>` أو `docs/<وصف>` أو `test/<وصف>` أو `refactor/<وصف>` (أحرف صغيرة وشرطات).
2. التعديل مع الاختبارات، ثم `npm run lint` و`npm test` و`npm run build` محلياً.
3. Pull Request إلى `main`. يعمل «Comprehensive CI» (النظافة، حارس وجهة النشر، lint، الاختبارات، البناء).
4. مراجعة الكود، ثم الدمج. النشر الإنتاجي بعد الدمج يتبع [`DEPLOYMENT_AUTHORITY.md`](DEPLOYMENT_AUTHORITY.md).

## سياسة التسمية

لا تُستعمل أسماء أدوات المساعدة البرمجية بوصفها أسماء لمكوّنات المشروع أو علامةً على طريقة تطويره، في:

- أسماء الملفات والمجلدات والفروع.
- رسائل Commit وعناوين Pull Requests وأوصافها.
- التعليقات داخل الكود والتوثيق وملفات README.
- ملفات التعليمات المؤقتة والبرومبتات وتقارير التطوير غير التشغيلية.

اكتب رسالة Commit تشرح التغيير البرمجي، لا من نفّذه. لا تُعدَّل بيانات المؤلف أو المساهم ولا تُحذف بيانات منشأ ملزمة.
وإن أضافت أداةٌ متصلة بـGitHub اسماً أو هويةً تلقائياً لا يمكن التحكم به فهذا قيدٌ في الأداة، ولا يُدّعى غيابه.

### ما لا تشمله السياسة

اسم خدمة يعتمد عليها البرنامج فعلاً (Gemini وOpenAI وتكاملات الذكاء الاصطناعي التشغيلية وأسماء النماذج ومفاتيح الإعداد)
واسم وظيفة أو مكوّن تشغيلي مثل `copilot` في واجهة الذكاء الاصطناعي: لا تُغيَّر لأن تغييرها يغيّر سلوك النظام.

## فحص النظافة

`npm run check:hygiene` (ويعمل في كل Pull Request). يفحص: أسماء المسارات، المحتوى، المراجع المكسورة في ملفات Markdown،
الملفات المؤقتة والمهجورة، واسم الفرع وعنوان الـPull Request ووصفه ورسائل Commit. اسم الفرع غير المطابق للنمط تنبيه فقط ولا يمنع الدمج.

عند فشله تُطبع المشكلة وطريقة إصلاحها. للاستثناء المبرَّر أضف المسار إلى `scripts/hygiene-allowlist.json` مع سبب.
